# Deliverable audit mode

Critique a finished visual deliverable the way a designer reads it: catalogue, deck, poster, page template, artboard, exported PDF. Evidence is the render, not the source. Do not cite class names, variables, file paths or data files here. When the render exposes data, logic, truncation or fabricated values, mark it in one line for Design or Module mode and do not open it in this report.

Use this mode when the artefact is a produced visual output. Use `design.md` when an interface exists in code and `file:line` evidence is available and useful. When a deliverable is generated by a template or script in the same project, audit the render here and route implementation defects to Design; the two reports stay separate and neither duplicates the other's findings.

## 1. Establish target and authority

- Identify what is under audit: canvas artboards, PDF, deck, HTML page, exported image. If the user already stated it, do not ask again.
- Rule source order: the project's `DESIGN.md` or design-system README, then recorded decisions in the project context, then general design principles. **Never invent a rule.** Do not write a threshold, ban or required component absent from the source; where the source is silent, label the observation a judgment.
- Establish the reader and the reading situation: two minutes on a phone, searching at a desk, three seconds on a wall. Use the context if it is available; otherwise ask once.

## 2. Scope

Honor scope the user already gave. Otherwise ask one choice question: **Focused** (one page type) · **Key pages** (the two or three most repeated and most seen page types; recommended) · **Full** (every page type). For repeating pages one example per type is enough; add the fullest and emptiest example when density varies materially.

## 3. Evidence: render first

- No finding without a render. If the user did not share one, produce it locally when possible (canvas files, HTML, PDF pages). If a render cannot be produced, that page is **unverified**; do not speculate.
- Inspect at true size: page dimensions and typical viewing distance for print, target device width for screen.
- Reuse one capture across several findings on the same page. Never redraw or regenerate a capture as evidence.

## 4. Order of attack: structure before detail

Read each page type in this order. If there is a structural problem higher up, record it before descending into detail.

1. **Purpose and reading order.** Does the page do one job; where does the eye start, where does it go, where does it stall.
2. **Hierarchy.** Does the order built by size, weight, colour and space match the real order of importance. Different things that look equal; equal things that look different.
3. **Rhythm and space.** Do block gaps sit on a scale; is the balance of filled and empty deliberate or residual. Are margins and header/footer positions consistent across page types.
4. **Typographic application.** Are scale steps used in the right place; are line length and leading readable; do uppercase labels and weight contrasts create noise; check broken headings and single-word lines.
5. **Colour and emphasis.** How many places carry the accent and what does it mark; if everything is emphasis, nothing is. Judge contrast against thresholds the source documents; do not call it low without measuring.
6. **Component consistency.** Do elements doing the same job look the same (label bands, numbered steps, chips, footnotes). Compare with sibling pages.
7. **Medium legibility.** Print: point size, hairline rules, grey text, how gradient bands reproduce, behaviour in black and white. Screen: what disappears in a reduced preview.

## 5. Writing rules

- At most three observations per heading. The whole report stays within two screens.
- Every observation carries: which page, where in the render (top left, masthead band, second column), what is visible, and the effect on the reader.
- Label each one: **[Observation]** measurable or plainly present in the render · **[Judgment]** a design call that is open to debate · **[Rule]** contrary to `DESIGN.md` or a recorded decision, with the source named.
- **Describe the defect and its mechanism; do not design the correction.** "The masthead band sits closer to the title than the section gap elsewhere on the page, so the two read as one block" is a finding. "Match that gap to the section spacing" is a remedy and belongs to the reader. Where useful, state the observable outcome that would show the finding resolved.
- No scores or percentages. Use the shared High / Medium / Low priorities from `reporting.md`: High breaks reading or defeats the page's purpose, Medium is friction, Low is polish.
- No technical language: class names, variables, file paths and patterns are out of scope here. Token names are acceptable for colour (terracotta, muted-dark) because they are design vocabulary.
- When the work under review is the user's own, do not condescend. State the position plainly and give the reasoning.
- Follow the project's language and typography conventions for the report itself.

## 6. Report format

Use `reporting.md` for priorities, evidence handling and coverage. Keep this mode's shape:

1. **Verdict** (two sentences): whether the page does its job, and the single largest problem.
2. **Findings** grouped under High / Medium / Low, each naming its capture.
3. **Unverified**: pages that could not be rendered or properties that could not be measured (contrast, a print proof), and who can verify them.
4. **Hand off to Design or Module**: data and logic problems as a one-line list.
5. One concrete next step.
